# グラフ型プレゼン（Graph Engineering）検証レポート

作成日: 2026-07-30 ／ 対象: 株式会社タイガーラボ ／ 検証物: [`demo.html`](./demo.html)

X記事「スライドをページではなくノードで設計する」について、内容の解説・技術的な事実確認・
当社での活用可否を検証した。**実際に動くプロトタイプを自社の営業ストーリーで作成済み**（`demo.html`）。

---

## 1. 記事の内容（非エンジニア向けの要約）

### 普通のスライドとの違い

| | 普通のPowerPoint | グラフ型プレゼン |
|---|---|---|
| 作るもの | 完成した「ページ」を100枚 | 情報の「点」と、点どうしの「線」を1セット |
| 見せ方 | ページを順にめくる | 1枚の図の上で、見せる部分だけを出し入れする |
| 聞き手の頭の中 | 前のページを記憶で繋ぐ | 繋がりが画面に描かれている |

紙芝居を1枚ずつめくるのが従来型。グラフ型は、**大きな路線図を1枚だけ用意しておいて、
話に合わせてカメラを寄せたり、関係ない駅を消したりする**やり方。

### 記事が言っている仕組み

1. **情報を「点（ノード）」にする** — 「人手が足りない」「AI研修」「Light 20万円」など、話に出る要素を1つずつ独立した部品にする。各部品は名前・種類・重要度・画面上の位置・どの場面で出すか、といった情報を持つ。
2. **関係を「線（エッジ）」にする** — 「AがBの原因」「AはBに含まれる」など、点と点のつながりを別データにする。
3. **場面が変わったら、図の状態を変える** — 記事の言う5つの処理：①出すものを中央へ ②出さないものを外へ逃がして薄く ③大事なものだけ拡大 ④線を順番に描く ⑤全体が画面に収まるようカメラを調整。
4. **動きは「差分」だけ考える** — 前の場面と次の場面を見比べて、増えた点だけふわっと出す、消える点は薄くする、格上げされた点は大きくする。これだけでアニメーションになる、というのが記事の実務的なコツ。

### 記事の主張のポイント

「情報を増やす人ではなく、複雑な情報を一瞬で理解させる人が高く売れる」——
資料の枚数ではなく**情報の構造を設計すること**に価値がある、という主張。ここは同意できる。

## 2. 事実確認：どこまで本当か

検証した結論を、**そのまま鵜呑みにできる部分**と**割り引くべき部分**に分けて記載する。

### ✅ 事実として正しい部分

- **技術は実在し、枯れている。** ノードとエッジを扱う描画ライブラリ（Cytoscape.js、React Flow、vis-network、Sigma.js 等）は10年以上の実績がある。2026年時点でも「関係の探索・分析にはCytoscape.js、編集UIにはReact Flow」という使い分けが定石。
- **記事の設計（データ構造と5処理）は、そのまま実装できる。** 今回、外部ライブラリを一切使わずゼロから実装して動作確認済み。**ノード26個・エッジ30本・7場面で破綻なし**（JSエラー0件、ノードの重なり0件、横スクロールなし）。
- **「差分でアニメーションする」は正しい実務判断。** 場面ごとに動きを手で作り込むと保守不能になる。前後の状態を比較して自動で動かす設計は、枚数が増えるほど効く。
- **効果が出る題材は確かにある。** 業務フロー、組織図、課題と打ち手の対応、サービスの内訳 —— 「要素どうしの関係」が主役の説明では、確実に従来のスライドより速く伝わる。

### ⚠️ 割り引くべき部分

- **「PowerPoint完全終了」は誇張。** PowerPointが強いのは描画性能ではなく、**①客先で編集できる ②印刷・PDF化できる ③誰でも作れる**の3点。グラフ型はこの3つがすべて弱い。置き換えではなく**併用**が正解。
- **「100枚を1枚に圧縮」は題材を選ぶ。** 圧縮できるのは関係で表せる情報だけ。実績紹介、料金表、写真、長文の条件面は、普通のスライドのほうが速く正確に伝わる。実際、今回のデモでも全26ノードに収まったのは「構造の説明」部分のみ。
- **「法人案件100万円」は、技術ではなく中身の値段。** 同じ仕組みでも、原稿を貰って図にするだけなら数十万円規模。100万円が成立するのは**情報設計（何をノードにするかを一緒に決める工程）を含めた場合**。記事はここを飛ばしている。
- **目新しさではない。** ズームで見せるプレゼン（Prezi）は2009年からある。今の差分は「AIを使えば、この手の作り込みが安く作れるようになった」という点であって、手法そのものの新規性ではない。

## 3. 当社での活用可否

**結論：活用できる。ただし「プレゼンツール」としてではなく、`①自社の営業武器` `②診断の納品形式` `③研修の教材` の3用途に絞るべき。**

当社は「AIを、"なんとなく"で終わらせない」を掲げ、自社をAIで運営していることを実績にしている。
**動くグラフ資料そのものが実力の証明になる**ため、他社より効果が大きい。

### 用途①：商談での自社説明（最優先・すぐ着手できる）

すでに `demo.html` として完成している。当社の営業ストーリー7場面をグラフ化したもの。

1. 課題（人手が足りない／属人化／社長の時間がない）
2. 原因まで分解
3. できることは3つ（サービスの柱）
4. 9つのメニューへ展開
5. Light / Standard / Full に接続
6. 進め方5ステップ
7. **全体像 —— ここまでの説明すべてが1枚に収まっている**

最後の7場面目が効く。「さっきまでバラバラに説明していたものが、実は全部つながっていた」を
画面で見せられる。**この体験自体が「AIでこういうものが作れる会社」の証明になる。**

さらに、ノードをクリックすると**その要素に直接つながる部分だけが残り、他が沈む**。
「うちは属人化が課題で…」と言われたら、その場でクリックして該当する打ち手だけを抽出できる。
台本どおりに進めなくてよい＝**商談の脱線に強い**。

### 用途②：AI活用診断の納品形式（値上げ根拠になる）

現状、深掘りレポート5万円〜の納品物はおそらく文書。これを

- **現状マップ**（業務・担当者・ツール・詰まりをノード化）
- **打ち手マップ**（どの詰まりに、どのメニューが効くか）

の2状態のグラフで納品すると、「なぜこの提案なのか」が一目でわかる。
文書と違い**関係の抜け漏れが視覚的に露呈する**ので、診断の質そのものも上がる。

### 用途③：実践AI研修の教材（15万円）

記事も「企業研修なら業務フローをクリックで分解」と書いており、ここは素直に有効。
受講企業の実際の業務フローをグラフ化し、**「どこがAIで置き換わるか」をその場でクリックして見せる**。
汎用スライドの研修との差別化になり、研修単価を上げられる。

## 4. 本命の提案：ヒアリング記録から、グラフを自動生成する

ここが当社にとっての最大の勝ち筋であり、**元記事が触れていない部分**。

グラフの中身は結局、下記のような**構造化データ（JSON）**でしかない。

```js
{ id:'c1', label:'手作業が多い', category:'原因',
  slideNumbers:[1,2,6], parentId:'p1', importance:2, x:430, y:180 }
```

つまり、

```
商談・ヒアリングの議事録  →  AIでノード／エッジのJSONに変換  →  グラフ資料が生成される
```

というパイプラインが組める。**当社が普段売っている「定型業務の仕組み化」「業務ツール・自動化」
そのもの**であり、自社で内製できる。

これが回ると、**1件ごとの制作コストが劇的に下がり、「顧客ごとの専用提案資料」を毎回作れるようになる。**
汎用資料しか出せない競合に対して、そのまま価格差の根拠になる。

> ※ 座標（x, y）だけはAI生成に向かない（重なる）。自動レイアウトを使うか、
> 業種別に3〜4種類の型を用意して当てはめる方式を推奨。

## 5. 商品化の案（既存の料金体系に合わせた）

| メニュー | 価格（税別） | 位置づけ |
|---|---|---|
| グラフ型 提案資料の制作 | **30万円〜** | Web・LP制作（30万円〜）と同格。原稿支給、5〜8場面 |
| AI活用診断 ＋ グラフ納品 | 深掘りレポート **+10万円** | 現状マップ／打ち手マップの2点 |
| 実践AI研修 ＋ 業務フローのグラフ化 | **30万円**（研修15万円＋15万円） | 受講企業の実フローを教材化 |
| 情報設計から伴走（研修・採用説明・全社説明用） | **60〜100万円** | 何をノードにするかの設計工程を含む。記事の「100万円」が成立するのはここ |
| 更新・保守 | **月1万円〜** | 既存のサイト／ツール保守と同枠 |

**原価の目安**：今回のデモは、既存LPのデザイン資産を流用して**実質1営業日相当**で構築できた。
土台（`demo.html`）を雛形として使い回せるため、2件目以降は主にコンテンツ設計の工数のみ。粗利は高い。

## 6. リスクと、向かないケース

必ず事前に握っておくべき点。

- **稟議・社内回覧にはPDFが要る。** 日本の中小企業案件では、決裁時に紙かPDFが回る。
  グラフ型は印刷に弱い。**必ず従来型のPDF資料を併走させる**こと。単独納品はしない。
- **納品後、顧客が自分で編集できない。** PowerPointと違い、更新は当社の作業になる。
  → 事前に伝えればトラブルにならず、むしろ**月額保守の根拠**になる。
- **本番で動かないリスク。** 客先のWi-Fi、プロジェクタ解像度、ブラウザ差。
  → 対策：単一HTMLファイルで完結させ（外部通信ゼロ）、オフラインで動くようにしてある。
  加えて、当日は**必ずPDFのバックアップを持参**する。
- **話し手が慣れていないと逆効果。** 情報が動く分、練習していないと迷子になる。
  → 商談投入前に社内で2回はリハーサルする。
- **向かない題材**：実績・お客様の声・料金表・写真主体の内容・長文の条件面。
  ここは従来のスライドのほうが速い。**混ぜて使う。**

## 7. 次のステップ（推奨）

| | 内容 | 目安 |
|---|---|---|
| 1 | `demo.html` の内容レビュー（表現・価格・ストーリーの確認） | 即日 |
| 2 | 実際の商談で3件使い、**説明にかかった時間**と**先方の質問の質**を記録 | 2〜3週間 |
| 3 | 効果が出れば、AI活用診断の納品形式に採用 | 1か月 |
| 4 | 議事録→JSON変換の自動化を内製（用途④の仕組み） | 1〜2か月 |
| 5 | 単品メニューとしてサイトに掲載 | 効果確認後 |

いきなり商品化せず、**まず自社の商談で使って効果を測る**のが最も安全で、
かつ「自社で使っているものを売る」という当社の一貫した売り方にも合う。

## 8. デモの使い方

`demo.html` をブラウザで開くだけ（インストール不要・オフライン動作・外部通信なし）。

| 操作 | 動作 |
|---|---|
| `→` / `←` キー、下部のボタン | 場面を進む／戻る |
| 下部のタブ（01〜07） | 任意の場面へジャンプ |
| **ノードをクリック** | その要素に直接つながる部分だけを残し、他を沈める |
| `Esc` またはノード以外をクリック | 抽出を解除 |

画面右の「いま、内部で起きていること」パネルは**説明用**。
記事にある5つの処理と、ノード1件分の中身が実際に動いているのが見える。
商談で使う際は、このパネルは外して全画面表示にする（`.inspector` を非表示にすればよい）。

### 技術メモ

- 外部ライブラリ不使用・単一HTMLファイル・通信ゼロ。社内ネットワークの制限を受けない。
- ノード／エッジのプロパティ名は元記事の設計にそのまま合わせてある（`slideNumbers`, `parentId`, `importance` など）。
- 5つの処理は、コード上も `centerVisible()` / `parkHidden()` / `scaleImportant()` / `stageEdges()` / `fitCamera()` という関数名で1対1に対応させてある。改造する際の入口になる。
- 内容を差し替えるには、ファイル冒頭の `NODES` / `EDGES` / `SLIDES` の3つの配列を書き換えるだけでよい。デザインやロジックには触れなくてよい。
- 既存LPのデザイントークン（`--bg`, `--cyan`, `--grad`, 明朝＋ゴシック）を継承しているため、サイトと見た目が揃う。
- 検索エンジンには載せない設定（`noindex`）。sitemap.xml にも追加していないため、SEOへの影響はない。
